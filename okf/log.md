## 2026-10-06 — Ctrl+LAmiga+RAmiga three-finger reset (UAOS-178)

* **Added** (`kernel/irq/ps2kbd.{c,h}`): `PS2Kbd_CheckResetChord()` — reboots via `System_Reboot()` when `g_kbd_mods.ctrl && super_left && super_right` are all held. Called after every modifier transition in the PS/2 IRQ handler (all 8 branches: L/R Super, L/R Alt, L/R Ctrl, Shift, Caps) so the last key of the chord completes it; release transitions can never satisfy the check.

No hardware/firmware reset chord exists on this machine (Mac reset chords need the power button), so the salute is implemented purely in-OS.
* **Verified**: `make kernel` builds and links `build/uaos-kernel.elf` clean; `PS2Kbd_CheckResetChord` resolves from both `ps2kbd.o` and `usbhid.o`. `System_Reboot` is terminal from IRQ/poll context by design (`cli` first, then 0xCF9/8042/triple-fault fallbacks). ## 2026-10-06 — Scheduler queue atomicity: stranded-EventPump desktop freeze (UAOS-265 follow-up)

* **Diagnosed** (bare-metal + QEMU): after the emit-composition fix landed, the MBP4,1 desktop froze minutes in — no mouse/keyboard, AGATest's animation stopped, but telnetd answered and the PIT kept ticking. Live `peek` on the box showed the EventPump's list node self-linked (`ln_Succ == ln_Pred == self`) while `tc_State == TASK_READY` — dequeued but never dispatched, unreachable by the scheduler. QEMU reproduced a complementary split-brain: pump node pointing *into* the pri-0 ready head (`ln_Succ == ln_Pred == &g_ready_heads[128]`) while the head was self-linked — i.e. the node-side stores of a `list_append` landed but the head-side stores never did (or an interleaved dequeue rewrote them). Injecting input IRQs via the QEMU monitor delivered a `Signal()` that `wait_remove`d the torn node and re-enqueued it — the pump self-healed and the display unfroze, proving the mechanism: **non-atomic scheduler list surgery torn by an IRQ**.
* **Root cause**: `do_schedule(0)` runs through the `int $0x80` *trap* gate, which preserves IF — `Task_Yield()`/`Task_CheckResched()` (Permit) reach it with interrupts live, so `ready_enqueue(prev)`/`ready_dequeue_highest()` could be interrupted by an IRQ that did its own `Signal()`/`Task_ScheduleFromIRQ()` queue ops on the same lists. `Task_CreateNative`/`Task_CreateX64` ran their `ready_enqueue` under `Forbid` only — Forbid suppresses dispatch, *not* IRQs — same tear window. And `Task_CreateX64` re-`memset`/`list_init` a REMOVED slot that could still be linked in a ready queue (RemTask leaves READY victims queued for the dequeue to drop), severing the list mid-node.
* **Fixed** (`kernel/exec/task.c`): all queue primitives — `ready_enqueue`, `ready_remove`, `ready_dequeue_highest`, `wait_enqueue`, `wait_remove` — now run `irq_save()`-atomic, and `do_schedule`'s whole pick+arm section (prev re-enqueue → dequeue → `g_current`/`Task_SwitchNext` arm) is wrapped in one `irq_save` region, closing every IRQ-tear window regardless of caller context. `ready_dequeue_highest` also guards the map-set-but-queue-drained NULL pop. `Task_CreateX64` unlinks a stale-linked REMOVED node before memset-reuse, and both create paths mark the slot `TASK_REMOVED` until `ready_enqueue` births it (IRQ-side walkers can see the slot as soon as `g_task_count` bumps).
* **Added** (safety net): `Task_WakeTimers` now scans `g_tasks` each tick for a stranded task — READY or WAITING with a self-linked node, not `g_current` — and re-links it after two consecutive sightings (the 2-tick vote skips the `list_init`→enqueue window of a task under construction). A strand now self-repairs within ~2 ticks and logs `[TASK] WARN: '<name>' stranded` instead of silently freezing the desktop.
* **Verified** in QEMU: 300 s soak under AGATest (84% CPU, continuous `WM_Invalidate*` → `EventPump_Wake` load) plus a PS/2 input storm via the monitor — EventPump held ~27% CPU / ~23 switches/s the whole run, display animated throughout, `g_strand_votes` never fired, no `[TASK] WARN`/`panic` in the serial log. Screenshot confirms the emit fix intact: AGATest's screen composites behind the shell window. **Bare-metal verified on the MBP4,1**: reflashed ISO boots clean, no punch-through flash, desktop stays responsive — freeze gone.

## 2026-10-06 — Long-running M68k app lifecycle (UAOS-247)

* **Fixed** (cycle-budget kill of blocked apps, `kernel/exec/exec_task.c`): the wrapper's 100M-cycle budget counted *cumulative* guest cycles, killing any app alive ~14 s — including correct programs parked in `Wait()`/`WaitPort()`. The budget now counts only *unblocked* cycles: the glue bumps `g_m68k_block_marks` whenever the guest naps in `Wait`/`WaitPort`/`WaitIO`/`WaitTOF`, and the slice loop resets its spin counter when the mark changes. Crossing 100M unblocked cycles emits a one-shot diagnostic PC-ring dump ("spin watchdog fired … continuing") and keeps running — an app blocked on IDCMP can stay up for hours; `SYS:Demos/SpinTest` (pure CPU spin) verified the watchdog fires but the task survives.

* **Fixed** (external halt invisible to blocked guests): `exec_Wait`, `exec_WaitPort`, `dos_Delay`, `WaitTOF` and the sliced glue waits now poll `task->m68k_halted` and `m68k_end_timeslice()` out to teardown, and the host-side modal wait loops (`wait_requester_internal`, the asl file requester, `wait_alert_internal`) check it too — a guest halted while parked inside a `Request`/`AutoRequest` requester no longer vetoes teardown forever.

* **Fixed** (close-window-quit, `kernel/exec/intuition_lib.c`): a WM close on an M68k task's *last* window now halts the guest when it never subscribed `IDCMP_CLOSEWINDOW` — previously the close was vetoed and the guest sat in `WaitPort` forever. Guests that do subscribe still get the message and exit on their own terms.

* **Fixed** (task-owned resource reclaim): `Task_Exit`/`stub_RemTask` now funnel through a full teardown — `Memcheck_FreeByOwner` (guest AllocMem blocks), `UAOS_Intuition_CleanupTask` (windows/screens/requesters, UAOS-265), new `HandleTable_FreeByOwner` + `VFS_FreeLock` (DOS files *and* locks — locks now send `ACTION_FREE_LOCK` so handler-side nodes die too), `UAOS_M68k_ReleaseTaskResources` (audio.device channels + open counts), `Task_ReleaseM68kRam` (guest RAM slot). `dos_Unlock` itself also routes through `VFS_FreeLock` — handler lock nodes no longer leak on the normal path either. New demos `LeakTest.s` (orphan screen+window), `LeakFile.s` (orphan file/lock), `SpinTest.s` (CPU spin) back the regression suite.

* **Fixed** (stale window bindings corrupting the *next* task — the OctaMED decrunch killer): two host-side caches were keyed by the guest RAM window pointer but never invalidated on task death, so a recycled slot inherited the dead task's state. (a) `chip_emu`'s DMA bindings — `g_display_ram`/`g_blit_ram`/`g_audio_ram` and floppy's `g_floppy_dma_ram` — let PIT-driven copper/blitter/audio/disk DMA keep writing into the window after the owner died; `chip_emu_unbind_ram()`/`floppy_unbind_ram()` now disarm every engine bound to the released window (display, blitter, audio, disk) without touching bindings owned by other live tasks. (b) `dos_lib.c`'s `g_heap_heads[]` host-side free-list mirror survived its owner, so the next tenant of the slot got the dead task's freelist head restored into a fresh window — freelist "nodes" pointing into the new program image produced the observed `pool head/magic clobbered` → `AllocMem insane size` → early exit chain during OctaMED's decrunch. `UAOS_Heap_ReleaseWindow()` drops the mirror entry at slot release. Root cause confirmed by the failure pattern: fresh-boot OctaMED always survived; only suite runs preceded by LeakTest/HelloWorld (which free and recycle the same slot) corrupted.

* **Verified** via `tests/qemu_m68k_lifecycle_test.py` (imports `qemu_layout_test.py`'s monitor+GDB harness; attaches `build/octamed.img` as virtio1): **24/24 checks** — boot → telnetd; LeakTest ×3 with window/screen retirement and RAM-slot recycling; LeakFile clean exit with zero owned handles; HelloWorld close-gadget halt+teardown; **OctaMED launches first attempt and survives a 150 s blocked soak with zero watchdog fires**, then external halt tears it down and releases the slot; SpinTest watchdog dump + external halt; RAM slots back at baseline; serial free of faults/panics/real wild-PCs. Note the hygiene filter distinguishes the watchdog's benign `first wild PC` diagnostic label from real `WILD-PC pc=` circuit-breaker hits, and OctaMED's known `pc=0` NULL-call flake (UAOS-234) is tolerated.

## 2026-10-06

* **Fixed** (UAOS-263, `kernel/net/{tcp,telnetd}` + `kernel/display/shell_win.c` + `kernel/exec/{task,bsdsocket_lib}.c` — telnetd session/socket leaks and stale-owner socket reuse): the audited `CLOSE_WAIT`-forever and stale-`ESTABLISHED` sessions had already been partially bounded by UAOS-223/-60, but the deeper hole remained: TCP socket-table slots are freed by `tcp_rx`/`tcp_tick` (IRQ/poll context) and reissued by `alloc_sock()` while telnetd pump/session tasks still hold the bare index — a stale pump could feed input from, push "[session closed]" output to, or `tcp_close()` an innocent *new* connection that reused the slot, and a pump killed without its exit path left the socket `ESTABLISHED` with no stack-side bound (reboot-only recovery, matching the card). Teardown backstops: `Telnetd_CleanupTask` + `ShellWin_RemoteCleanupTask` run from `Task_Exit()` (the only reachable teardown path for native tasks — `stub_RemTask` can't target them), reclaiming pump ctx/session/slot/socket whatever killed the task; `open_remote_shell` rolls back `remote_inuse` if `Task_CreateNative` fails. Also: a SYN matching `TIME_WAIT` now retires the entry so a fast reconnect isn't RST'd by the dying incarnation. QEMU-verified on the rebuilt ISO: ~50 connect/FIN/abort churn cycles including 8-simultaneous bursts, `netstat` shows only listener + live sessions with zero `CLOSE_WAIT`/`FIN_WAIT` strays, `telnetd STATUS`/`taskdump` show no leaked pump/session tasks, busy banner correct at 4-session cap, serial log clean.

## 2026-10-05

* **Fixed** (UAOS-265 follow-up, `kernel/exec/intuition_lib.c` — guest screen emit punched through overlapping host windows): bare-metal audit on the MBP4,1 showed the *physical* display clean while `screenshot` JPEGs carried transient alien bands, plus a live repro: dragging a host window (Calc) over AGATest's custom screen flashed demo content through the window. Root cause — `UAOS_Intuition_FlushScreenBitmap()` ran the pen-cache emit / planar decode on the guest's own dispatch context in **direct mode** (no `FB_BeginDraw` frame), so `FB_BlitARGB`/`FB_PutPixel` wrote VRAM immediately and the blit overwrote whatever host window sat on top. Fix routes the flush through the WM damage path instead: refresh `g_scr_pens` for the dirty rect under the owner's bound RAM window, then `WM_InvalidateDesktopRect`/`WM_InvalidateRect` — the pump's composed repaint emits the pens *behind* overlapping windows inside one frame. Same for the `WA_SuperBitMap` branch (invalidates the client rect; `intu_draw_fn` re-renders it in-frame). Also clamped a real OOB in `scr_emit_pens`: damage extending past the screen's left/top edge produced negative `bx0`/`by0` and indexed the pen cache before the row/buffer, emitting foreign memory through the LUT. Verified QEMU 1024×768: AGATest screen+window still emits correctly and composites behind the shell window; metal re-verify on MBP4,1 pending (drag-over-screen should show no flash).

* **Fixed** (UAOS-265, `kernel/exec/intuition_lib.c` — transient full-screen false-color corruption, reproduced bare-metal and QEMU): Intuition window/screen slots survived their owning M68k task's exit — `Task_Exit()` released the per-task RAM window but never retired `g_intu_wins`/`g_intu_screens`, so host render paths kept decoding guest `BitMap`/`ColorMap`/pen pointers through whatever `g_ram` was bound next (the shared window, or a *reused* window belonging to a different task — guest addresses are only unique per window). A stale front screen's emit path (`scr_decode_pens` → `scr_build_lut` → `scr_emit_pens`) painted a planar-decode of foreign memory through a foreign palette — nibble-quantized OCS colours, complete alien desktop — directly into the back buffer mid-frame. `UAOS_Intuition_FlushScreenBitmap()` didn't even bind the owner's window, so a guest flush could emit the same foreign decode. Fix is two-layered: (a) new `UAOS_Intuition_CleanupTask(UaosTask*)` walks the dying task's requesters/alerts/windows/screens — closes WM handles, drops windows opened by other tasks on a dying screen, clears `g_scr_cache_bm`/`g_workbench_screen`, retires slots — called from `Task_Exit()` *before* `Task_ReleaseM68kRam()` and from `stub_RemTask()` (which bypassed `Task_Exit` entirely); (b) `window_is_orphaned`/`screen_is_orphaned` predicates + `retire_orphaned_screen()` guard every render entry point (`intu_draw_fn`, both backdrop impls, `FlushScreenBitmap`, `PollFrontScreenBitmap`, `intu_screen_vacate`, `ApplyFrontScreenPalette`), and `FlushScreenBitmap` now binds the screen owner's window around the emit. `intuition_CloseScreen`/`CloseWorkbench` invalidate the pen cache for freed bitmaps.
