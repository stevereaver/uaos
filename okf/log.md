# OKF Change Log

## 2026-09-25

* **Fixed**: `kernel/net/tcp.c` — RX ring overflow no longer corrupts the stream. `tcp_send_seg` advertised a constant 4095 window regardless of free space, and a full ring silently dropped segment tails while `rcv_nxt` still ACKed them. Now the window field tracks real `rbuf_free` space (0-window when full), `rcv_nxt` advances only by bytes actually queued (drop-and-NACK so retransmit recovers), retransmit overlap is trimmed and out-of-order segments dup-ACKed (`tcp_rx_data`), a FIN only counts once preceding data is delivered, data is accepted in the half-close states (`FIN_WAIT_1/2`, `CLOSE_WAIT`), and `tcp_recv` pushes a window-update ACK when a full ring drains. Verified with a host-side harness driving the state machine through overflow/partial-queue/retransmit/out-of-order/FIN races (30 checks). (UAOS-56)
* **Audited**: live telnetd service (192.168.10.84:23) via interactive session + raw-socket protocol probes plus code review of `kernel/net/telnetd.c`, `kernel/net/tcp.c`, and the remote-session path in `kernel/display/shell_win.c`. Findings tracked under umbrella card UAOS-47 (children UAOS-48..61): CRLF double-newline, CSI literal-byte leakage, Ctrl-C/vkey collision with no remote interrupt, missing output IAC-escaping, 64-byte input-queue loss, serialized single-session accept with unreachable busy banner, unrecoverable wedge after `netstop`, TCP send-window/single-segment-retx/RX-drop-but-ACK gaps, blocking serial mirror on every `inst_print`, per-keystroke full-line repaint, unguarded GUI/destructive commands, no dead-peer timeout, and ops polish items. No code changed. (UAOS-47)
* **Added**: `C:telnetd` — unauthenticated remote-shell daemon for debugging. `kernel/net/telnetd.c` runs a `telnetd` task that listens on TCP port 23 (`PORT=` override), sends the RFC 854 greeting (`WILL ECHO`, `WILL SGA`, `DO SGA`), and bridges each accepted socket to a remote `ShellInstance` through a small NVT state machine (IAC filtering, sub-negotiation consumption, escaped-`0xFF`, CR/LF normalisation, `ESC [` arrow keys to shell vkey codes). `kernel/shell/cmd_telnetd.c` registers the `telnetd` native command (`PORT/K/N` template); `scripts/build_iso.sh` compiles both sources and generates the `C:telnetd` stub. (UAOS-45)
* **Updated**: `kernel/display/shell_win.c` / `shell_win.h` — remote shell sessions. `ShellInstance` gained `remote`/`remote_sock`/`remote_dead`/`remote_inuse` fields and four dedicated slots past `MAX_SHELLS`; `inst_print`/`shell_print_raw` send over TCP via `remote_send`; a remote line editor mirrors the window editor with ANSI repaints; `endcli` marks the session dead through `close_shell`, disconnects are signalled via `ShellWin_RemoteKill`, and `ShellWin_RemoteOpen`/`RemoteFeed`/`RemoteIsDead` form the daemon-facing API. `vim`/`ed` inline editors refuse remote sessions. (UAOS-45)
* **Fixed**: `kernel/net/tcp.c` — two `SYN_RECEIVED` bugs that made inbound connections unreliable. (1) A retransmitted SYN matching a half-open socket was silently swallowed, and since `ip_send` drops the first SYN-ACK while the ARP cache is cold, handshakes could never complete once the initial SYN-ACK was lost — `tcp_rx` now replays the saved SYN-ACK on a duplicate SYN. (2) `SYN_RECEIVED` sockets had no timeout and leaked socket slots forever; they now expire via `conn_timer`. (UAOS-45)
* **Fixed**: `kernel/drivers/virtio_net.c` — `virtio_net_send` used one shared `g_tx_hdr_buf` and descriptor 0 with no serialization while senders can run from task context *and* the NIC IRQ handler (TCP ACKs inside `virtio_net_poll` → `tcp_rx`). Concurrent sends corrupted each other's frames; bad-checksum segments left holes the single-segment TCP retransmit model cannot recover, stalling connections. The claim/fill/notify sequence is now wrapped in `Disable()`/`Enable()`. (UAOS-45)
* **Verified**: QEMU user-mode net with `hostfwd=tcp::2323-:23` — `nc` receives the banner and `RAM:>` prompt, `version`/`dir` output streams correctly, `endcli` prints `Closing CLI...`/`[session closed]` and frees the slot, and a second connection gets a fresh shell. (UAOS-45)
* **Updated**: `okf/kernel/net/index.md` — documented telnetd, the `SYN_RECEIVED` fixes, and VirtIO-Net TX serialization; `okf/kernel/display/index.md` — documented remote shell sessions; `okf/index.md` — net entry now mentions telnetd. (UAOS-45)

## 2026-09-24

* **Updated**: `kernel/drivers/virtio_net.c` / `virtio_net.h` — added the modern virtio-1.0 transport for non-transitional `1af4:1041` devices (QEMU `-device virtio-net-pci` on q35/OVMF, `disable-legacy=on`). The driver now walks PCI vendor capabilities for common/notify/ISR/device-config regions, negotiates `VIRTIO_F_VERSION_1` + `VIRTIO_NET_F_MAC` with the FEATURES_OK handshake, publishes 64-bit desc/avail/used addresses through common config, enables queues, and rings the notify-region doorbell at `notify_off*notify_off_multiplier`. A twist specific to this codebase: OVMF maps the 64-bit BAR at ~768 GB, outside the 4GB identity map, so when capability BARs are unmappable the driver routes every register access through the `VIRTIO_PCI_CAP_PCI_CFG` config-space window (cap type 5: driver writes bar/offset/length, device proxies via `pci_cfg_data`) instead of dereferencing MMIO — the same fallback SeaBIOS uses. `g_hdr_len` selects the 10- vs 12-byte `virtio_net_hdr`; MAC comes from the device-config cap; reset polls `device_status` until 0. Verified on QEMU q35: modern device (disable-legacy=on) completes DHCP (10.0.2.15); transitional/legacy path (1af4:1000) also verified. (UAOS-40)

## 2026-09-24

* **Fixed**: post-format `makedir` failure on a mounted FAT32 partition — `format Device=DH0: Name=wb fat32` previously tried to mount by the FAT label `wb`, which cannot resolve to a block device, while the existing DH0 handler retained pre-format cached geometry. Added `VFS_RemountPartition()` and changed both native format command paths to refresh/remount under the stable device display name (`DH0`); `Name=` now remains solely the disk label. Runtime confirmed the remount (`Mounted as DH0:`), exposing a second return-value bug: FAT `ACTION_CREATE_DIR` returns a positive lock handle, but `VFS_MkDir` accepted only `DOSTRUE`, falsely reporting failure and leaking the lock after successful creation. VFS now accepts the lock, frees it with `ACTION_FREE_LOCK`, and returns success. Runtime then showed long pauses and non-persistent directory entries: VirtIO-SCSI sampled the command queue's `used_idx` after notify, so VirtualBox could complete a small request before the wait began; the waiter captured the completed index and timed out waiting for the next one, while retries consumed mismatched completions. Completion now compares against an independent last-consumed used-index shadow initialized with the queue. Runtime then confirmed timing was fixed but directory entries were still not visible. `fat32_write_dir_entry` now verifies the exact 32-byte entry by immediate readback and retries 3x; the FAT handler no longer reports success if the newly created path cannot be reopened. Directory creation and reopen then passed but `dir` enumeration stayed empty. The native x86-64 `DosPacket` ABI stored `dp_Arg1`–`dp_Arg7` and `DoPkt` arguments as `int32_t`, and VFS/dos.library explicitly truncated 30 native path, buffer, and `FileInfoBlock` pointers. Packet arguments now use `intptr_t`, with all truncating casts removed; action codes, results, handles, and M68k-visible values remain 32-bit. Widening packet arguments did not fix FAT enumeration, so `VFS_ReadDir` now uses a direct `FatHandler_ReadDir` path (open, `FAT32_ReadDir`, close) for FAT handlers while retaining generic packet EXAMINE enumeration for other handlers. Runtime proved persistence because a second mkdir of the same name correctly failed as already existing, while `dir` remained empty. The direct FAT enumeration wrapper's 4.5KB temporary stack arrays were removed; `VfsDirEnt` is now a shared named structure and `FatHandler_ReadDir` fills the caller's array directly. Entries still persisted while listing stayed empty; `cmd_dir.c` itself allocated 256 `VfsDirEnt` records (about 18KB) on the command stack, overflowing/corrupting the kernel task stack when enumeration wrote results. The directory workspace now uses static storage. The actual shell command was then traced: migrated userspace `C:dir` calls `uaos_opendir/readdir`, while kernel `sys_opendir` was RAMFS-only (`VFS_ResolveDir` + `RamFsNode*`) and could never enumerate handler-backed FAT volumes. Syscall directory handles now support RAMFS node iteration and cached generic `VfsDirEnt` results from `VFS_ReadDir`; `sys_readdir` marshals either source to `UaosUserDirent`. Full ISO build succeeds; final VirtualBox confirmation pending. (UAOS-41)

## 2026-09-24

* **Fixed**: `kernel/drivers/virtio_net.c` — virtio-net was completely dead on VirtualBox (init succeeded, DHCP timed out, no TX/RX). Root cause: the driver hardcoded the virtqueue layout for 256 entries and ignored the read-only legacy `QUEUE_SIZE` register; VirtualBox's VirtioCore fixes every virtqueue at `VIRTQ_SIZE = 1024` and derives `GCPhysVirtqAvail`/`GCPhysVirtqUsed` from it (avail at base+16K, used at the next 4K boundary), so the device read avail entries from memory past the 16KB queue buffer and never saw posted descriptors. The driver now reads `QUEUE_SIZE` per queue (up to `VIRTQ_MAX_SIZE` = 1024), lays out desc/avail/used rings at the reported size, and posts up to `VNET_RX_BUFS` = 256 RX buffers. (UAOS-38)
* **Updated**: `documentation/manual.md` and `okf/kernel/net/index.md` — documented the device-reported queue size handling. (UAOS-38)

* **Fixed**: `makedir` (and potentially other userspace commands) failing with "Failed to create directory." — userspace binaries were compiled *without* `-mno-red-zone`, so GCC placed `makedir`'s 256-byte `path` buffer straddling the SysV red zone below `%rsp`; the `INT 0x80` entry pushes ~160 bytes (CPU frame + saved GPRs) onto the user stack (ring-0 tasks, no privilege stack switch), clobbering `path[0..119]` → `sys_mkdir` received an empty string → `VFS_MkDir("RAM:")` returned -1. ## 2026-09-25

* **Fixed**: `kernel/drivers/virtio_net.c` — `virtio_net_send()` waited on `g_txq_last_used != g_txq_used->idx` before overwriting the shared TX buffer, an inverted condition that can never clear once the device posts TX used entries. QEMU never posts them so the wait was a no-op; VirtualBox does, so every send after the first spun the full bound with IRQs disabled and the system froze (telnet connect hard-locked the VM). Now waits on the real outstanding count (`avail->idx - used->idx != 0`) and latches `g_tx_no_used` after one progress-free timeout so QEMU keeps the old fast path. Also: `virtio_net_poll()` only rings the RX doorbell when RX descriptors were actually re-added (doorbell = VM exit; callers poll in tight loops). (UAOS-46)
